## 1. Overview

The `web/` directory is the **full-stack web application layer** of the Heat-Pulse project. It provides an interactive geospatial dashboard that visualises weather forecasts, energy production estimates, and statistical analytics for cities in Azerbaijan (and potentially other regions).

The application is divided into two sub-systems:

| Sub-system | Directory | Technology |
|---|---|---|
| REST API backend | `web/backend/` | Python · FastAPI · DuckDB |
| Browser frontend | `web/frontend/src/` | Vanilla JS · Leaflet · Chart.js · Tailwind CSS |

The backend **serves data** from a local DuckDB database and pre-computed JSON files. The frontend **consumes** that data and renders it as an interactive map with a slide-out analytics sidebar.

## 3. `backend/`

The backend folder contains the Python FastAPI application that acts as the data access layer. It reads from two sources: a **DuckDB database** (`data/weather.duckdb` located at the project root) and two **pre-computed JSON files** stored locally in `data_web/`.

---

### 3.1 `data_web/`

This subdirectory holds two large JSON files that are the primary data sources for the analytics sidebar. They are pre-generated by the pipeline in `src/` and are served statically via `main.py`.

#### `weather_predictions.json` — 740 KB

**Purpose:** Contains 30-day weather forecast data for every city tracked by the project.

**Structure:**
```json
{
  "cities": {
    "Baku": [
      {
        "date": "2025-05-01",
        "temperature_2m_max": 28.4,
        "temperature_2m_min": 18.1,
        "relative_humidity_2m_mean": 62,
        "weather_category": "Clear Sky",
        "impact_score": 0.73,
        "persistence_alert_level": "LOW"
      },
      ...
    ],
    "Ganja": [ ... ],
    ...
  }
}
```

**Key fields per record:**

| Field | Type | Description |
|---|---|---|
| `date` | string (YYYY-MM-DD) | Forecast date |
| `temperature_2m_max` | float | Maximum temperature at 2 m height (°C) |
| `temperature_2m_min` | float | Minimum temperature at 2 m height (°C) |
| `relative_humidity_2m_mean` | float | Mean relative humidity (%) |
| `weather_category` | string | Human-readable condition label (e.g. "Clear Sky", "Cloudy") |
| `impact_score` | float [0–1] | Composite score representing the severity of weather impact on energy systems |
| `persistence_alert_level` | string | Alert level based on consecutive persistence of extreme conditions (e.g. "LOW", "MEDIUM", "HIGH") |

**Why it matters:** This file drives the 30-day forecast table, the daily impact score bar, and the condition icon shown in the left panel of the sidebar. It is the primary source for short-term weather intelligence.

---

#### `energy_forecast_30days.json` — 28,262 KB

**Purpose:** Contains **hourly energy production forecasts** for wind turbines and solar panels at each city location over the next 30 days. This is the largest file in the project and drives all energy-related charts and statistics.

**Structure:**
```json
{
  "locations": {
    "Baku": [
      {
        "year": 2025, "month": 5, "day": 1, "hour": 0,
        "Envision_wind_kWh": 142.3,
        "Fuhrlander_wind_kWh": 98.7,
        "Jinko_Solar_kWh": 0.0,
        "Trina_Solar_kWh": 0.0
      },
      ...
    ]
  },
  "model_metrics": [
    {
      "target": "temperature_2m",
      "test_r2": 0.9812,
      "test_rmse": 1.34
    },
    {
      "target": "wind_speed_10m",
      "test_r2": 0.8741,
      "test_rmse": 2.17
    },
    {
      "target": "shortwave_radiation",
      "test_r2": 0.9103
    }
  ]
}
```

**Key fields per hourly record:**

| Field | Description |
|---|---|
| `year`, `month`, `day`, `hour` | Timestamp components for the forecast hour |
| `Envision_wind_kWh` | Energy produced by the Envision wind turbine model (kWh) |
| `Fuhrlander_wind_kWh` | Energy produced by the Fuhrlander wind turbine model (kWh) |
| `Jinko_Solar_kWh` | Energy produced by Jinko solar panels (kWh) |
| `Trina_Solar_kWh` | Energy produced by Trina solar panels (kWh) |

**`model_metrics` array:** Contains ML model accuracy metrics (R² and RMSE) for the underlying prediction models. These are displayed in the sidebar under "Model Reliability".

**Why it matters:** This file is the backbone of the energy analytics. `main.py` aggregates the hourly rows into daily totals for wind and solar, then returns them to the frontend. The file's large size (28 MB) reflects the high temporal resolution (hourly) and multi-turbine/panel data across all city locations.

### 3.2 `main.py` — 10 KB

**Purpose:** The **FastAPI application entrypoint**. Defines two REST API endpoints that are consumed by the frontend.

**How to run:**
```bash
uvicorn web.backend.main:app --reload --port 8000
```

#### Endpoint 1: `GET /api/weather`

Returns the **latest temperature, latitude, and longitude** for every city, read directly from the DuckDB database.

```
Query: SELECT city, temperature_2m_max, latitude, longitude
       FROM raw.raw_forecast
       QUALIFY ROW_NUMBER() OVER (PARTITION BY city ORDER BY time DESC) = 1
```

Used by: `App.js → fetchWeatherData()` to place markers on the Leaflet map.

**Response shape:**
```json
{
  "status": "success",
  "count": 12,
  "data": [
    { "city": "baku", "temp": 27.3, "lat": 40.41, "lon": 49.87 },
    ...
  ]
}
```

#### Endpoint 2: `GET /api/details/{city_name}`

The **primary analytics endpoint**. Returns a rich payload combining weather forecast, energy forecast, historical data, and model accuracy for a given city.

**Processing steps inside this endpoint:**

1. **Load weather JSON** — reads `weather_predictions.json`, performs case-insensitive key lookup for the city name, and extracts 30 daily forecast records.
2. **Load energy JSON** — reads `energy_forecast_30days.json`, aggregates hourly rows into daily `wind` and `solar` totals using a `defaultdict`.
3. **Query DuckDB** — merges `raw.raw_historical` and `raw.raw_forecast` tables using a `UNION ALL + QUALIFY ROW_NUMBER()` pattern to deduplicate overlapping dates (historical data takes priority). Returns temperature, humidity, wind speed, and solar radiation per day.
4. **Fallback logic** — if DuckDB is unavailable or returns no data, falls back gracefully to the JSON forecast data.
5. **Returns combined payload** with keys: `weather`, `forecast`, `energy_forecast`, `energy`, `accuracy_metrics`, `hist_temps`, `hist_full`.

**Why it matters:** This single endpoint is the hub of the entire dashboard. It handles complex multi-source data fusion, case-insensitive lookups, time-series deduplication, and graceful degradation — all in one function. It is the most critical piece of backend logic in the project.

## 4. `frontend/`

The frontend is a **pure browser application** — no build step required. It uses CDN-hosted libraries and consists of a single HTML entry point that loads three JavaScript modules.

---

### 4.1 `package.json` — 0 KB (Placeholder)

**Current state:** Empty file. No Node.js packages are actually installed or required since all dependencies are loaded via CDN in `index.html`.

**Why it exists:** Placeholder for future tooling (e.g. ESLint, a bundler like Vite, or npm scripts). At present it can be safely ignored.

### 4.2 `src/index.html` — 10 KB

**Purpose:** The **single HTML document** that bootstraps the entire application. Defines the page structure, loads all external and local scripts, and sets up the DOM skeleton.

#### Structure breakdown:

| Section | Description |
|---|---|
| `<head>` | Loads Tailwind CSS (CDN), Leaflet CSS (CDN), Google Fonts (Inter), and custom inline styles |
| `#map` | Full-viewport Leaflet map, fixed behind all UI elements |
| `<header>` | Contains the "HEAT PULSE" branding, a city search input, and a "Colorful Mode" toggle button |
| `#overlay` | Semi-transparent blur overlay that appears when the sidebar opens |
| `#sidebar` | Two-column slide-in panel: left 28% (city weather summary) + right 72% (charts and tables) |
| `#admin-modal` | Modal dialog for manually adding a city with name, lat, lon, and temperature |
| `<script>` tags | Loads Leaflet, Chart.js, then `weather-icons.js`, `charts.js`, and `App.js` in dependency order |

**Critical inline CSS:**
- `#map` is `position: fixed; z-index: 1` — behind all overlays.
- `.ui-overlay` uses `pointer-events: none` on the container but restores them on children, allowing the map to remain interactive under transparent UI areas.
- `.table-scroll` defines a custom thin scrollbar for the forecast tables.

**Why it matters:** This file is the user's entry point. All visual layout, z-index layering, and library loading order is defined here. Changing script load order (e.g. loading `App.js` before `Chart.js`) would break the application.

### 4.3 `src/App.js` — 25 KB

**Purpose:** The **main application controller**. Manages map initialisation, data fetching, sidebar state, and DOM rendering.

#### Key global state variables:

| Variable | Type | Purpose |
|---|---|---|
| `globalData` | Array | City list returned by `/api/weather` |
| `geoLayer` | Leaflet Layer | GeoJSON overlay for colorful mode |
| `colorfulMode` | Boolean | Tracks whether the heatmap color overlay is active |
| `tempChartInst` | Chart.js instance | Reference to the temperature distribution histogram |
| `energyChartInst` | Chart.js instance | Reference to the energy bar chart |

#### Key functions:

**`fetchWeatherData()`**
- Calls `GET /api/weather`
- Populates `globalData` and calls `displayCities()`

**`displayCities(cities)`**
- Iterates city data and places a small Leaflet marker at each coordinate
- Each marker has a click handler that calls `openDetails()` and flies the map to that city

**`openDetails(city)`**
- The central UX function. Opens the sidebar, calls `GET /api/details/{city}`, then orchestrates all render calls:
  - `renderWeatherSection()` — city name, weather icon, temperature
  - `renderImpactSection()` — impact score gauge
  - `renderMetricsSection()` — model R² / RMSE values, total energy
  - `renderAllCharts()` and `initCharts()` — delegates to `charts.js`
  - `renderForecastTable()` — 30-day weather table
  - `renderEnergyTable()` — 30-day energy table
- Uses a `setTimeout(520ms)` delay to wait for the CSS sidebar slide-in transition before rendering charts (prevents zero-size canvas issues).

**`renderWeatherSection(cityName, w)`**
- Injects city name, animated SVG weather icon (from `weather-icons.js`), max temperature, and weather condition label into the left panel.

**`renderImpactSection(w)`**
- Displays the `impact_score` as a visual progress bar and the `persistence_alert_level` as a colour-coded badge.

**`renderMetricsSection(m, e)`**
- Shows model accuracy (R² for temperature, wind, solar) and total 30-day wind/solar energy in kWh.

**`renderForecastTable(fc)`** and **`renderEnergyTable(ef)`**
- Inject scrollable HTML tables with per-day weather and energy data.

**Search functionality**
- Listens to the `#map-search` input and filters `globalData` by city name (case-insensitive), then calls `openDetails()` on the first match.

**Colorful Mode toggle**
- Switches the map tile layer from dark monochrome to a color tile, and optionally overlays a GeoJSON temperature heatmap using circle markers colour-coded from blue (cold) to red (hot).

**Admin modal**
- Accepts a city name, latitude, longitude, and temperature, then dynamically adds a new marker to the map without a backend call.

**Why it matters:** `App.js` is the orchestration layer of the frontend. It owns all side effects — API calls, DOM mutations, map interactions, and event listeners. It depends on `charts.js` and `weather-icons.js` but neither depends on it.

### 4.4 `src/charts.js` — 39 KB

**Purpose:** A dedicated **Chart.js rendering module** containing all statistical chart logic. This is the largest and most analytically sophisticated file in the project.

#### Constants:

| Constant | Purpose |
|---|---|
| `CHART_IDS` | Array of 9 canvas element IDs managed by this module |
| `SEASON_ORDER / LABELS / COLORS` | Maps season names to display labels and colours |
| `DARK` | Shared theme config (grid colour, tick colour, legend colour) for the dark UI |

#### Statistical utility functions:

**`fiveNum(arr)`**
- Computes the five-number summary (min, Q1, median, Q3, max) with IQR-based whisker clipping (1.5× IQR rule). Used for box plots.

**`kruskalWallis(groups)`**
- Implements the Kruskal-Wallis H-test, a non-parametric ANOVA for comparing seasonal temperature distributions. Returns the H statistic and approximate p-value via `chi2CDF()`.

**`lnG(z)`**
- Lanczos approximation of the log-gamma function, required internally by `chi2CDF()`.

#### Dark theme helpers:

**`darkScales(xL, yL)`** — Returns Chart.js `scales` config with dark grid lines and tick colours.  
**`darkPlugins(title, sub)`** — Returns Chart.js `plugins` config with dark legend and title.  
**`base(extra)`** — Returns `{responsive: true, maintainAspectRatio: false}` base config for all charts.

#### Chart rendering functions:

| Function | Chart Type | Description |
|---|---|---|
| `chart2_SeasonalBoxplot()` | Box Plot | Temperature distribution per season (Spring/Summer/Autumn/Winter). Includes Kruskal-Wallis p-value in the subtitle. |
| `chart3_QQ()` | Scatter | Q-Q plot comparing temperature distribution against a theoretical normal distribution to assess normality. |
| `chart4_TimeSeries()` | Line | Full historical + forecast temperature time series (max, min, mean) plotted chronologically. |
| `chart5_Decomposition()` | Multi-line | Trend, seasonal, and residual decomposition of the temperature time series (simple moving average approach). |
| `chart6_YearOverYear()` | Line | Overlays temperature curves from multiple years on the same axis (Jan–Dec) to show inter-annual variability. |
| `chart7_CalendarHeatmap()` | Custom Canvas | Draws a calendar-style heatmap (day-of-year × year) directly on a canvas using 2D context, colour-coded by temperature. |
| `chart8_AllCities()` | Bar | Compares max temperature across all cities in the current 30-day forecast period. |
| `chart9_Scatter()` | Scatter | Temperature vs. humidity scatter plot, coloured by season. |
| `chart10_CorrMatrix()` | Custom Canvas | Draws a correlation matrix heatmap for temperature, humidity, wind speed, and solar radiation. |

**`renderAllCharts(apiResult)`**
- Master entry point called by `App.js`. Destroys all existing chart instances, then builds the right-panel HTML shell (`_buildRightPanelShell()`), and triggers all 9 chart functions inside a `setTimeout` to let the DOM update first.

**`initCharts(fc, ef, ht)`**
- Initialises the two "summary" charts shown at the top of the right panel: the temperature histogram (`tempChart` canvas) and the wind/solar energy stacked bar (`energyChart` canvas). These are separate from the 9 detailed charts.

**Why it matters:** `charts.js` is the analytical heart of the dashboard. It transforms raw time-series data into 11 distinct statistical visualisations, including non-trivial statistical tests (Kruskal-Wallis), signal decomposition, and custom canvas-drawn charts. At 39 KB, it contains more logic than any other file in the project.

### 4.5 `src/weather-icons.js` — 18 KB

**Purpose:** A **pure data module** that exports a single object `WEATHER_ICONS` mapping weather condition strings to animated inline SVG icons.

#### How it works:

```javascript
const WEATHER_ICONS = {
  "Clear Sky": `<svg>...</svg>`,
  "Cloudy":    `<svg>...</svg>`,
  "Cloudy-Sunny": `<svg>...</svg>`,
  // ... more conditions
};

function getWeatherIcon(condition) {
  return WEATHER_ICONS[condition] ?? WEATHER_ICONS["Clear Sky"];
}
```

`getWeatherIcon(condition)` is called by `App.js → renderWeatherSection()` and returns the matching SVG string, which is injected directly into the DOM.

#### Implemented condition icons:

| Condition | Animation |
|---|---|
| Clear Sky | Spinning sun rays + pulsing sun core |
| Cloudy | Floating cloud layers with depth |
| Cloudy-Sunny | Spinning rays behind a floating cloud |
| Rainy | Falling rain drops |
| Stormy | Lightning bolt flash effect |
| Snowy | Falling snowflake particles |
| Foggy | Drifting horizontal fog bands |
| Windy | Moving wind arc lines |

All icons are **self-contained SVGs with embedded CSS animations** using `@keyframes`. They require no external image files, no network requests, and no canvas — making them instant to render.

**Why it matters:** The icons are the primary visual cue for weather conditions in the sidebar left panel. Using inline animated SVGs instead of image files means zero loading latency, full CSS theming compatibility, and no external dependencies.

## 6. Key Design Decisions

**No build step.** The frontend uses CDN-hosted Tailwind, Leaflet, and Chart.js. This trades bundle optimisation for simplicity — ideal for a data science project where the frontend is a dashboard, not a product.

**setTimeout for chart rendering.** Charts are initialised 520 ms after the sidebar opens, matching the CSS transition duration. This prevents Chart.js from drawing into a zero-width canvas before the DOM layout completes.

**Multi-source data fusion in a single endpoint.** The `/api/details` endpoint merges DuckDB historical data with JSON forecast data using SQL deduplication (`ROW_NUMBER() OVER PARTITION BY`). This keeps the frontend simple — one API call gives it everything it needs.

**Graceful degradation.** If DuckDB is unavailable (e.g., the database file doesn't exist), `main.py` falls back to JSON forecast data. The frontend always gets a usable response.

**Case-insensitive city matching.** Both the backend (Python `next(k for k in ... if k.lower() == target_lc)`) and the frontend search handle case differences between the database (lowercase city names) and the JSON files (Title Case keys).
